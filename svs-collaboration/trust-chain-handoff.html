03/Scoping correction

It's Vault PKI — not EJBCA

!
The agenda lists “PKI/EJBCA.” There is no EJBCA anywhere in this codebase. The PKI backend actually implemented and exercised end-to-end is HashiCorp Vault — PKI secrets engine, SSH secrets engine, and KV v2 for registry credentials — reached via a local vault-agent proxy using AppRole authentication. If SVS is independently standardizing on EJBCA, that's a real decision to make explicitly now: Vault-only, EJBCA-only, or Vault-fronting-EJBCA are materially different scopes of work, and getting this wrong changes what SVS staffs for.

What exists

  • TPM-backed CSR generation on-device
  • vault.csyang.org — PKI sign, SSH CA, KV credential store
  • AppRole auth via vault-agent UDS proxy

What doesn't

  • No EJBCA instance, config, or reference — anywhere
  • No confirmed production topology decision
  • No Vault unseal-key / root-CA escrow plan (slide 5)

05/Container image trust chain

Where the chain is whole, and where it isn't

SVS side — mostly undefined

1Build container image
2cosign sign — private key custody: no owner defined
3Push to OCI registry — registry itself does not exist

WNC side — implemented

4container-ota-agent receives pull command over UDS from kms-mqtt-trigger
5Ephemeral registry creds requested from kms-cert-manager (Vault KV read)
6cosign verify --key cosign.pub (transparency log check disabled)
7podman pull by digest, only if verify passed
8Credentials wiped (docker_logout)
?
Highest-leverage open question: cosign.pub is baked into the device image at build time — there is no remote key-rotation path. Whoever holds the private signing key is the actual root of trust for every container this fleet ever runs, and that ownership is currently undefined on either side.
06/SIEM & production-line provisioning

Two more gaps, both already load-bearing

Log ingestion — no SIEM plugged in

Device pipeline is fully built: PII/secret masking, HMAC-SHA256 line integrity, disk-backed retry queue, separate 90-day audit stream, firewall-event classification. CrowdSec (host IDS) is installed.

→TLS forward target is a build-time loopback placeholder — real endpoint deliberately not shipped in firmware
→CrowdSec has no acquisition config or notification wiring — binary + service ship, nothing tells it what to watch

Production-line IDevID — confirmed broken

Manufacturing issues each device's permanent IDevID; the field-commission flow only ever consumes it. That manufacturing process is entirely external to this repo.

!Live 2026-07-30 test: provision.csyang.org completes TLS but rejects the MQTT connect at the app layer — untrusted CA and/or unregistered device_id
!Three manufacturing-enrollment design docs referenced by name in code comments do not exist in this repo
!
No device shipped today can complete real field commissioning until the broker trusts a manufacturing-issued IDevID CA — this is not a future risk, it is the current state. Full detail: 03-siem-and-production-provisioning.md.

09/Open questions

What we need SVS to answer

1
Is csyang.org the production domain?
Or a lab stand-in SVS will replace — this decides whether device-side endpoint/cert-pinning config is final.
2
Vault, EJBCA, or both?
Blocks any further PKI-related scoping — see slide 4.
3
Who signs container images?
The private cosign key's custody model is the actual root of trust for the whole OTA chain.
4
Does SVS already run an OCI registry, DMS, or monitoring stack?
Or is this greenfield build for our fleet?
5
Who owns Vault HA and key escrow?
Is this inside SVS's existing operational practice for other products?
6
Is RADIUS/WPA3-Enterprise in scope for this product?
Or is WPA2-PSK an accepted tradeoff for the target OT deployment?
7
Is a SIEM (e.g. Wazuh) already standard in SVS's stack?
Or does one need to be stood up for this product specifically — the device pipeline is ready to feed it today.
8
Where does production-line IDevID enrollment actually happen?
Who owns provision.csyang.org's CA trust store — this blocks real field commissioning right now.
